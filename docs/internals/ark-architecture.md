# ARK product boundary

ARK combines T3 Code's interface and conversation system with ATOM's feature domains from `main`. The T3 source baseline is `441a4ebd65543fa414797253eb31cc02f8811e32`; the ATOM baseline is `a578162`. Upstream MIT attribution remains in the root license.

The conversation system keeps its original provider adapters, thinking timeline, streaming, attachments, conversation persistence and recovery. ATOM is not a provider in this architecture. Its former chat interface does not become a second chat inside ARK.

ATOM's domain code remains in the independent `atom/` workspace while it is ported. ARK's server owns one feature runtime, whose process lifetime follows the server's Effect scope. It uses feature-only startup so speech-model loading does not block agents or knowledge. The existing backend still validates and persists domain operations. Feature state and mutations cross typed, authenticated ARK RPC boundaries; clients do not get a raw runtime command channel.

The workspace reads real agents, memory facts, notes, skills and saved briefs. Agent availability is writable and only reports success after the backend emits the saved Ready/Paused state. Profile edits use the current soul version, and note edits use a content revision, to reject stale editors. Source import reuses the bounded preview/token flow and preserves correction conflicts. Source operations require both filesystem-read and orchestration-operate access; clients never get a raw runtime command channel. Chat retrieves facts, notes and skill pages through authenticated read-only MCP tools. ARK-owned and personal skills are selected separately; skill contents cannot grant permissions. Agent-profile task launches stay disabled until provider boundaries enforce their tool kits and folder restrictions; native approval modes are not equivalent to those restrictions. The companion capability remains unported. Chat-linked work reads the conversation system’s existing shell state; earlier ATOM jobs stay explicitly historical.

T3's native schedules, provider settings and source-control features remain active. Feature-only startup disables ATOM's old task runner, routine clock, Telegram/API chat consumers and automatic brief/source-analysis clock so they cannot compete with the unified orchestration system. ATOM's routines, model routing and approval mechanisms cannot simply overwrite those domains: each needs an explicit integration boundary as it is ported. In particular, provider credentials and chat transcript ownership stay with the conversation system; feature-owned permissions and state stay deterministic in their owning service.

Development uses `.ark/userdata` for ARK's conversation server and `atom/data` for its feature runtime. The child’s memory/helper/settings paths are explicitly set so ambient ATOM environment variables cannot redirect it into installed state. Neither installed ATOM data nor `~/.t3/userdata` is opened or migrated automatically. The earlier `.atom-t3` prototype data is left in place and is not used by the ARK launcher. Existing history, remembered grants and identity need a deliberate migration before replacing an installation.

Folder reviews pair the existing helper grant with a separate directory identity in `atom/data/ark-agent-folders.json`. A review is bound to the agent's current access revision and expires after five minutes; confirmation resolves and checks the directory again. Missing, changed or unrecorded identities never become verified automatically. This deliberately preserves earlier grants while requiring identity review before future restricted launches. The grant and identity stores cannot commit atomically: failure leaves an unverified grant or a removed grant, never inferred approval. Access mutations require access-write, plus filesystem-read for review or grant, and are not exposed as model tools. The read-only policy tool reports launch blockers. These records do not yet enforce a provider session's tools; profile launches remain disabled.

Reply drafting uses the selected native provider’s isolated text-generation path. Claude disables customizations, tools, external MCP and session persistence; managed MCP configurations are refused. Codex must confirm its isolated permission profile, disable inherited skills/plugins and report no active MCP tools before receiving draft content. Other providers have no draft runner and cannot silently substitute another provider. Only explicitly selected, revision-checked context excerpts are included. Stop and surface disposal interrupt the scoped child process.

Computer use is a separate checked capability, not a replacement provider. Each action is bound to the current thread, provider session and run, with a single host-wide action lease. Persisted chat events cancel work when its owning turn stops or changes. The native adapter keeps window references separate per session, reuses ATOM's observation/action policy and refuses ARK's own app. A declined approval blocks computer work for that turn. Remembered chat access is stored separately from T3's provider approval mode, and never bypasses sensitive-action approvals. Stop waits for the owned helper to finish; an unconfirmed cancellation blocks further input until restart. Screenshots are returned only to the requesting tool, not broadcast in activity state.

Jev/Laya choose only between prepared, checked button plans. The main chat model still prepares plans and reviews observations. Jev receives bounded goals, window labels and candidate plans, excluding screenshots and editable-field values. Its key stays in the environment's private secret store, and requests reject redirects and use a short deadline. Laya is optional and is never downloaded or warmed merely by opening a feature page.

Voice capture and playback belong to the requesting client; using ATOM's host microphone or speaker would act on the wrong device for remote sessions. Typed voice requests use the same feature child for local Whisper/Kokoro processing, without starting its legacy conversation loop. Audio is returned only to the requester, never broadcast or added to chat history. Surface disposal cancels pending work and releases media tracks/object URLs. ARK's Kokoro worker forbids model downloads; feature startup never warms voice models. Successful read-aloud requests reuse the loaded worker for up to a minute; cancellation or idle expiry releases it.

The feature runtime currently requires the Mac backend and its independent dependencies. The web RPC can serve authenticated remote clients, but native capability helpers still need to be included in ARK's desktop distribution. The preserved SwiftUI app is source reference, not the new ARK interface.
