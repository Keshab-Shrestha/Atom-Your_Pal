# Task branch starting points and discovery

ADR-173, 2026-10-19. The Dashboard discovers `atom/task-N` and legacy `zeno/task-N` branches from existing agent folder grants and active, freshly checked projects whose folder is the repository root. A subfolder project alone does not authorize reading changes across its parent repository; use its scoped Git workspace. Archived, removed, missing or rejected project folders do not add discovery authority. Independently retained agent grants still apply.

New task worktrees explicitly start at the resolved creation-time HEAD commit. After successful branch creation, the host records its canonical repository, branch, exact commit and optional local creation branch ref in an exclusive owner-only JSON record under `data/worktrees/.branch-bases/` (beside task trees). Filenames hash the repository/branch pair. Reuse never overwrites or backfills this record. A recording failure stops preparation before the worker starts. Existing branches keep their original names and receive no invented history or migration.

Saved reviews compare the exact starting commit to the task head, even if another branch is checked out or the creation branch advances or disappears. This is the net change since task creation, including subsequent merged changes; it is not an inferred PR merge base. Commits use the same starting point. Behind counts measure commits on the current recorded creation branch not reachable from the task, using local refs only. Missing refs and detached starts leave behind unknown, rather than claiming zero. Nothing fetches automatically.

Older branches without a record use the merge base with locally known `origin/HEAD`, otherwise the current non-task branch. Cards say **Estimated base**. A checked-out task branch without a usable remote default cannot compare with itself: it shows an unavailable warning. Corrupt records, missing saved commit objects and failed comparisons refuse the patch instead of falling back to estimates or claiming no changes. The saved commit is not a new Git retention ref: a destructive rewrite plus pruning can make it unavailable, which is reported explicitly.

Cards show the saved/estimated commit, local behind count and explicit Refresh. Refresh after a task's host commit; there is no background watcher. Refresh clears an expanded old patch. Existing limits remain 50 commits, 200 file summaries, 200,000 patch characters and 400 rendered patch lines, with capped/truncated presentation. Git subprocesses have time/output limits, fixed arguments, no hooks/fsmonitor/external diff/textconv, stripped inherited Git routing and no interactive prompts. Metadata is comparison data, never permission or executable instructions. Host preparation/commit policy otherwise remains unchanged.

Project discovery adds read authority only. Push still requires the existing agent folder grant plus a separate explicit confirmation in the app; its button is disabled when that authority is absent. Push remains task-branch-only, to existing `origin`, without force or hooks. No branch deletion, remote fetch, pull, merge, conflict prediction, PR integration or new grant is introduced.
