# Reviewed edits from a Codex preview input

Implemented in source on 2026-10-18, ADR-166. This adds a separately approved text proposal for one existing short input file. It does not automatically apply a shell diff or attest that proposed text came from the sandbox. Tests and live acceptance remain skipped by request.

## Source receipts and review

A successful, cleaned-up ProjectShellPreview returns a host-generated receipt when required-undo support is available. Its private task-local record retains the canonical task root, selected relative input paths and the host-computed original SHA-256 hashes. Command output cannot populate this record. Failed, cancelled, truncated or cleanup-uncertain previews do not issue receipts. Empty-input previews have nothing to edit. Receipts are discarded at task end/restart and cannot be used by another worker/task/chat.

Project folders workers with current project admission and required-undo support get `atom_ReviewPreviewEdit`. Exact fields are preview_id, file_path and proposed complete content. Only an existing selected input from this worker's receipt is eligible. Two attempts share the inspection/preview busy slot. An eligible input is consumed before awaited checks, including on refusal, so uncertain operations cannot silently replay. Invalid receipts still consume an attempt. No other path, new file, deletion, generated-file import or multi-file apply is accepted. While review is pending, the target is held against this worker's ordinary host Write/Edit. Refusal, error or uncertainty keeps that hold for the rest of the task and blocks another review of the same file; only confirmed success releases it. Write/Edit recheck holds after awaited policy/read/preparation. Already-dispatched filesystem operations cannot be recalled, and this is not a global lock on other tasks, MCP servers or external editors. Ending the worker aborts owned signals before clearing receipts/holds.

The host runs current native Read policy, reads bounded regular UTF-8 source text and compares it with the saved hash. Native Write/plan/floor/taint checks then run on the proposed text, followed by a fresh explicit review card. The entire relative path and original/replacement text must fit the existing 600-character reason; oversized and unchanged proposals refuse. JSON quoting plus escaped whitespace preserves the review through the card bridge's whitespace normalization. This deliberately supports only short files. Hidden controls and detected secret shapes are refused in old/new text; pattern filtering does not identify every secret. Native policy may require additional cards and its ordinary best-effort checkpoint hook can run before the final review.

Approval waiting is bounded at 120 seconds, with task Stop and current source-project/worker/task checks. Deadline cancellation cannot cause a late approval to commit. After approval, hash, file identity and permissions are checked again. Only regular single-link files owned by the running user are eligible; links, special mode bits and changed paths refuse. Files and proposed text have a 256 KiB read/encoding bound, although the complete-review card imposes a much smaller practical limit.

## Required checkpoint and replacement

The host-only guardPreviewEdit store method requires a running non-advisory job. It verifies or creates a private numbered original-content snapshot, checks its exact size/hash, and fsyncs the snapshot and private checkpoint directories. Missing storage, skipped/damaged copies, exhausted existing checkpoint limits, incompatible baselines, unsupported fsync or permission errors refuse the edit. Unlike ordinary worktree hooks, this operation requires a snapshot even inside the task worktree. An earlier edit with a different original baseline, or an already guarded row for the file, refuses rather than silently reusing the wrong undo copy.

An additive checkpoints.guarded column defaults to zero for existing rows. Before replacement, a guarded row records the expected replacement hash. Normal task completion and startup reconciliation leave that hash fixed. Later file edits therefore remain conflicts instead of becoming an inferred approved result. If the operation stops after arming but before replacement, the original file may show as Changed/conflicted; no automatic rollback/retry occurs. Ordinary rows keep their previous finish/recovery behavior.

After checkpoint arming there are no JavaScript awaits through staging and replacement. The host creates a unique exclusive staging file beside the target, writes/fsyncs it, preserves ordinary permission bits, and rechecks its bytes/identity, target bytes/identity and parent identity before atomic rename. It verifies resulting content afterward. This serializes the final phase against other host JavaScript tools, but is **not a filesystem compare-and-swap**: another editor/process can still race between checks and rename. No cross-file or filesystem/SQLite transaction, perfect concurrent-write protection, power-loss guarantee or metadata preservation beyond ordinary mode bits is claimed. ACLs, extended attributes and other inode metadata are not copied. Synchronous filesystem operations have no hard wall-time deadline.

Post-dispatch uncertainty is reported without rollback or automatic retry. Staging cleanup failure also prevents a success claim and may leave the uniquely named file. For Git projects the operation edits the task worktree, retaining existing task-branch/commit behavior; it does not copy to the user's current branch.

## Undo and scope

The existing task Board checkpoint/Undo interface is reused after the task ends. Guarded rows use bounded no-follow hashes for current-file conflict detection and backup verification. Normal Undo refuses a changed/missing/nonregular file or damaged snapshot. The existing explicitly confirmed Force behavior is retained; this upgrade does not turn force into an automatic fallback. Retention, task deletion, current path/grant checks and existing restore behavior still apply. A verified copy is not an indefinite retention promise, automatic rollback or atomic conflict check against external editors.

Board observations keep the existing bounded target summary, name, timing and generic outcome. Proposed/old text, receipts and hashes are not added to tool-event logging; ordinary provider context and private approval presentation necessarily contain the proposed review text. No new Swift UI, network endpoint, dependency, model/provider call or shell privilege is introduced. Ordinary Write/Edit remain separate, with their existing checkpoint policy; the same worker's host Write/Edit also enforce the pending/failed review hold.
